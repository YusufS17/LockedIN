# Private friends beta — architecture and readiness

Prepared 2026-10-03. This is a proposed implementation contract plus a locally tested, **non-production** Swift prototype. No backend, authentication, networking, deployment, real friend session, or native focus tracking has been implemented by this slice. The app still uses labelled seeded companions. No provider or paid service has been selected.

## First usable beta

Two to eight signed-in friends join an invite-only study session, see one another’s chosen subject and goal, start together, and see coarse self-reported focus/break/away states. A lobby may contain just its creator; starting requires at least two admitted members. Solo study keeps its existing offline path. A frozen session roster can remain visible when someone disconnects; disconnection is not proof of distraction or early exit.

Default interaction is supportive, with no public ranking or teasing. Initial beta has no chat, public discovery, real money, app/site activity sharing, or claims that it measures attention. Friends explicitly choose text to share; their private post-session goal review remains local. Room-wide state does not include a private interruption event log. Shared persistent furniture and group-earned upgrades are a separate required gate after admission, timing and individual outcomes are reliable.

## Minimal architecture

Use a backend with authenticated HTTPS commands, a durable transactional datastore, and an authenticated stream of full room snapshots. For rooms of at most eight people, full snapshots keep recovery simpler than a delta/event reconstruction protocol. The iPhone sends commands and renders snapshots; it does not publish authoritative room documents or reward totals.

| Boundary | Required behavior |
| --- | --- |
| Account | Authentication middleware supplies an opaque stable account ID. Never accept the actor ID from a request body. Store credentials in the platform credential store; no backend administrative secret in the app. |
| Private membership | Every room read, write, subscription and snapshot refresh checks current membership. No public room enumeration. Owner-only invites and start; participants can change only their own study information and aggregate presence. |
| Invite | Single-use, recipient-bound, expiring secret, revocable by owner. Store a hash of the secret, use secure random generation, avoid secret logging, and rate-limit redemption. Admission and invite consumption occur in one transaction with capacity enforcement. A forwarded link must not admit another account. |
| Room/session | Persistent room ID and per-run session ID are distinct. One durable participant UUID per `(sessionID, accountID)`; a uniqueness constraint enforces the mapping. Owner and roster freeze at start for the first beta. |
| Ordering | Every accepted room mutation atomically increments its revision. Commands include `expectedRevision`; stale writes fail and return/refetch current state. Clients never merge two conflicting snapshots with the same revision. |
| Transport recovery | Reauthenticate, recheck membership and fetch a full snapshot before enabling controls. Keep the last confirmed room visible with “Reconnecting”. Discard callbacks from closed connection generations. Never queue offline start/finish/reward writes as if confirmed. |
| Command retry | Persist an idempotency key plus command result under the authenticated account/session. A timed-out request retries the same key. Compare-and-set revisions alone do not provide exactly-once acknowledgement. |
| Persistence | Commit membership, consumed invite, revision and command result together. Publish after commit; an outbox/replay mechanism must recover from commit-without-broadcast failures. The store, not an in-process singleton, arbitrates concurrent requests. |

Invitation delivery can initially be a manually shared link; no email/contact access is necessary. Recipient binding still needs an authenticated account lookup or owner-approved pending join. Select and implement one before beta; the local fixture assumes the recipient’s account UUID is already known. Owning a link is not membership.

Server-side member removal, room closure and account deletion must invalidate read/subscription access immediately. Removed clients clear private cached snapshots when access is denied. A retained internal outcome record may preserve the historical participant UUID without granting access to the room. These operations are **not** implemented in the prototype, which intentionally models an append-only lobby and frozen study roster. It also has no host transfer or cancellation. Before beta, define how a departed host's session terminates or continues without losing individual outcomes, and provide an explicit cancellation state that never creates completion rewards. Do not deploy these omissions as an access policy.

## State and reconnect rules

Proposed lifecycle: `lobby → studying → finished`. Starting freezes roster, duration, break allowance and other rules in one transaction. Use a server start/deadline and per-participant pause/break accounting so device wall-clock changes cannot complete a shared session. The existing solo `FocusClock` pauses on breaks; preserve that meaning when designing each participant’s authoritative completion deadline. A shared start does not require falsely marking everybody complete when one person finishes.

Presence is an enumerated aggregate: ready, focusing, on break, away, finished. “Focusing” means the timer is running and the participant has not reported a break; it does not mean verified attention. A heartbeat timeout can mark connectivity as unavailable, separately from study state. Server timestamps and a documented expiry window are required; iOS suspension and reconnect must never invent an attention verdict. Breaks, early leave and expiry need explicit commands and server validation before rewards become available.

Snapshots carry a schema version, session ID, monotonic revision, frozen rules, participant IDs, permitted profile/study information and coarse states. Reject unsupported schema versions rather than silently discarding fields. The prototype now contains session/owner/revision/phase/member IDs/presence plus optional explicitly shared subject/goal and recipient-scoped envelopes. Duration, schema evolution and authoritative timer semantics remain subsequent work. Each shared subject is nonempty and at most 40 characters; goals are nonempty and at most 120 characters when an intent is shared (the whole intent remains optional). Both must be trimmed and exclude control characters. Only a member can publish or withdraw their own text, only in the lobby; starting freezes it. Production must also enforce request-body byte limits. No private review text enters the authority or snapshot.

For a given session, a client accepts a newer **full** snapshot even if revisions were missed, ignores older snapshots, and treats an identical revision as a harmless repeat. Different contents at the same revision require a fresh authoritative read. Account-to-participant identity cannot change during restoration. State cannot return to an earlier phase. Bind each connection to its authenticated account and expected session; a higher revision from another room is irrelevant. An untrusted JSON payload is not authenticated just because the reducer accepts its structure.

On app relaunch, decode and validate a saved snapshot against the signed-in account and expected session, retain its participant UUIDs/revision, and mark it disconnected. The prototype's startup-only `restoreCachedSnapshot` enforces that distinction. Persisting a snapshot to disk, protecting it by account, and validating future schema versions remain adapter work. Keep unreadable cache isolated instead of creating a replacement participant. Offline cache hydration cannot reauthorize membership or grant rewards.

The fixture's `FriendsConnection` now implements connection generations and reconnect gating around the lower-level `FriendsReplica`. Each attempt gets a new UUID token. Cache hydration cannot enable controls. Stream frames before the fresh read are ignored; an equal current snapshot from that read can enable controls without inventing a new server revision. An older read cannot. Closed-generation stream/read/denial/disconnect callbacks are ignored. Full newer snapshots can skip missed revisions. A contradictory or invalid current-generation frame closes that generation, disables commands and preserves the last valid display; recovery requires a new attempt. Current permission denial clears the private cached snapshot. Ordinary network loss retains it with controls disabled. There is no offline command queue.

This is a pure reducer contract, not an authenticated transport. A real adapter must obtain `recipientID` from verified channel identity, reauthorise each read/subscription, invoke `receiveFreshRead` only for a fresh membership-checked request, and deliver permission denial to the current generation. A fabricated envelope is not authentication. TLS, credentials/token expiry, server-side subscription revocation, heartbeat expiry and actual persistence remain unimplemented. Backend revisions solve order, not transport authenticity. The real service must also make read-to-subscription handoff atomic or replay full snapshots newer than the acknowledged read revision. Because this reducer deliberately ignores pre-read stream frames, an adapter that loses its last update in that handoff could remain stale until another snapshot; actual transport tests must cover that race.

## Reward identity and migration

Today `WorldStore.applySession` keys `WorldState.sessionRewards` by `SessionParticipant.id`, not by `ActiveStudySession.id` or account ID. `ActiveStudySession`/`StudySessionStore` retain the roster UUID through local restoration. Preserve this contract.

For a new online session, allocate the participant UUID once at admission and use that exact UUID when constructing the local `SessionParticipant`. Save and restore it; do not call `makeRoster` on reconnect, replace it with an account ID, or mint a UUID while showing results. Each new session gets a new participant UUID. Existing local sessions and receipts retain their original IDs; do not retroactively convert a running solo session into an online session.

The backend must eventually issue an immutable terminal outcome keyed by that participant UUID, with a unique reward ledger entry and an atomic balance update. The current local reward store can prevent ordinary repeated local display from paying twice, but it cannot establish cross-device authority, resist modified client balances, or atomically commit against a remote database. An explicit migration/ownership decision is required before syncing balances or shared purchases. The prototype only verifies identity preservation; it does not award coins, prove eligibility or implement a reward ledger.

Do not map the prototype’s owner-triggered `finish` directly to production completion. It exists solely to test terminal ordering. In beta, authoritative timers, recorded breaks, early leave and frozen rules determine each person’s outcome. One owner cannot certify everybody’s study effort. Reuse actual reward regression fixtures when adding the online adapter.

## Implementation and release gates

1. **Backend and auth prerequisites:** provision a development environment with a transactional datastore, TLS API endpoint, authenticated snapshot transport, secret management and logs with invite/personal-data redaction. Choose an account provider and configure its app identity, redirect/callback handling, token verification and expiry/revocation behavior. Supply the app’s public environment configuration through build settings and credentials through secure developer/server storage. No provider-specific capability or pricing assumption is made here.
2. **Admission and security:** implement invite delivery/recipient resolution, rate limits, private row/document access, subscription authorization, transactional capacity, stable IDs, removal/closure/account deletion and idempotency. Test outsiders, forwarded/expired/reused/revoked invites, a simultaneous eighth/ninth join and immediate access revocation against the real service.
3. **App integration:** the local demo now supports 2–8 participants in balanced seating areas, per-person bounded subject/goal and frozen intent/UUID restoration (see CLUB_EXPANSION.md for exact runtime evidence). Add an online session adapter without replacing the verified offline store. Bind restored state to the authenticated account/session, preserve participant identity, and label “Reconnecting” and self-reported states. Obtain explicit shared-text choices and enforce the same validation on the service. Implement server timing, per-person breaks/leave and terminal outcome receipts; verify retries and multi-device account behavior.
4. **Shared room progression:** define group contribution rules; persist layout, catalogue item IDs, ownership and purchase/contribution receipts transactionally. Reconnects and retries cannot duplicate group upgrades. This remains separate from the prototype’s session roster.
5. **Physical-device prerequisites:** two iPhones on supported OS versions, two distinct test accounts, access to the same development backend, and a signed build installed through the team’s chosen development/TestFlight route. Configure the necessary signing/app identity and invite-link routing for that route. Also test one account on two clients to exercise duplicate outcomes. No native blocking entitlement is assumed or required for this presence beta.
6. **Acceptance evidence:** capture both devices showing the same session, admitted roster, subject/goal and transitions. Exercise foreground/background, network loss, relaunch, token expiry, removal, duplicate commands/outcomes, stale and reordered updates, and a changed device clock. Document actual physical-device durations and failure results. Test persistent shared-room upgrades and reward replay after backend restart before closing the multiplayer milestone.

## Local evidence

The isolated [FriendsPrototype](../Tools/FriendsPrototype/README.md) contains Foundation-only models, an in-memory authority and a client snapshot reducer. Its disposable runner compiles with `swiftc` and deletes its temporary executable/module cache. It does not read/write app preferences, touch simulator data, or connect to a service.

On 2026-10-03 the runner passed 83 assertions covering private access, recipient/expiry/revocation/single-use invites, roster bounds, stale revisions, self-only aggregate presence and shared intent, frozen membership/text, text validation/withdrawal, snapshot ordering/conflicts, restored identity, recipient-scoped cache hydration and wire-field allowlists. Two independent client reducers converge after dropped/reordered frames. Reconnect fixtures cover closed-generation callbacks, stale reads, equal-revision fresh reads, disabled offline commands, invalid-frame connection closure and current-generation denial/cache clearing. These are sequential contract fixtures, not tests of backend transactions, actual concurrency, security infrastructure or real devices. The app target is unchanged by this work.
